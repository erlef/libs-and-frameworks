# Libraries & Frameworks Working Group: Meeting Summary

Oct 28, 2026 · @DanJanowski

Attendees joined from Munich, Kraków (Software Mansion), Alabama, Tula and Sweden, among others. The meeting covered four topics.

## 1. UUID support in OTP

- Jakub Gonet couldn't attend. Occupied with other things (Popcorn 1.0). plans to come back to UUID issue. He has been working on a candidate UUID implementation for OTP.
- The goal is to replace the many duplicated UUID implementations across Erlang, Elixir and others with one standard building block. The precedent is JSON landing in OTP.
- Rickard on the OTP team advised submitting a PR directly rather than writing an EEP first.
- Placement is still open. UUIDs need strong random bytes, so the code may end up in the `crypto` application.
- Members were invited to suggest other commonly duplicated functionality that belongs in OTP.

## 2. Package stewardship

The problem: once a package is published to Hex, there's no formal policy for what happens when it goes unmaintained or how to track its level of support. Users can't easily tell whether a package is maintained, receiving security fixes, or superseded. Today the only route is an informal one: contacting the Hex team to take a package over.

### Experiences shared

- **George:** His company has locked down Hex.pm access over vulnerability concerns. It now pulls dependencies from GitHub and scans its own forks. Frank does something similar for Nerves by maintaining patch sets for slow-moving upstreams.
- **Brujo:** He did the opposite at his company, spending about a month moving years-stale forks back to current Hex releases.
- **Brujo:** He published `inaka_mixer` as a maintained fork when `mixer` was abandoned. The original is now gone from Hex, which leaves an awkward package-name/app-name mismatch that should be cleaned up.

### Ideas discussed

- Hex could show a status banner or warning on unmaintained packages. It could also suggest alternatives, either forks with the same API or different packages solving the same problem.
- Hex could print warnings at dependency-fetch time, using predefined messages only and avoiding npm-style free-form messages.
- A standard README status banner, with date codes so it's clear when it's stale.
- Jonatan's suggestion: a metadata file shipped with releases (fork-of, maintenance status, accepting contributions) that Hex can display.
- Supporting a package diverging under a new name and later converging back.
- **Succession claims need attestation.** A package simply declaring "I succeed X" is too easy to abuse for malware. One option is maintainer confirmation, with a fallback of Hex team discretion after about a year of no response.
- Hex could email owners of packages untouched for 2–3 years. The email would explain the options: hand over to a fork or adopter, or retire the package.
- Adoption is preferable to deprecation for packages that are still used and not superseded. Vetting adopters' intentions is a resource and trust problem.
- The security/CNA process faces the same difficulty reaching maintainers and should be able to flag unmaintained packages.

### Discoveries during the meeting

- Hex already supports `mix hex.retire` with reasons such as "deprecated", and it shows a warning on the package page. Brujo retired one of his archived packages on the spot.
- Retirement is per version, and the warning appears only on the retired version.
- rebar3 gives no warning when a retired plugin is used. This should be addressed.

## 3. Missing "parity" features (OpenTelemetry as the example)

- The BEAM ecosystem lags others on table-stakes features that enterprises expect. For example, OpenTelemetry tracing in other ecosystems extends down through database adapters, which ours doesn't.
- The argument isn't only about enterprise. Shared, purpose-built libraries such as SDKs get security-scanned once, so users don't each reintroduce the same bugs. Ash's security scanning was cited as an example.

### Pain points

- Erlang OTel metrics are marked "experimental." The code isn't immature; there's no CNCF reviewer able to approve the Erlang code for promotion to stable.
- Library authors get confusing guidance on whether to use `telemetry` or OpenTelemetry directly. The two have different interfaces.
- Documentation, discoverability and inconsistent use of the OTel registry are also weak.
- Some adapters, such as the Oban one, exist but aren't actively maintained.
- Funding is the underlying problem: this work is unglamorous and rarely gets paid time.

### Opportunities

- **Membrane (Software Mansion):** The team is planning a paid dashboard feature, similar to Oban Pro. The proof of concept uses a custom HTTP endpoint, and the existing Membrane OTel repos are 2–4 years stale. The group encouraged building on OpenTelemetry instead. That would mean maintaining one thing rather than two, and it would showcase what OTel can do on the BEAM.
- **Voyager**, an Observer-style monitoring tool, rolls its own telemetry layer. It could be nudged toward an OTel backend.
- Small, consistent contributions from many projects could close most of the gap.

## 4. Official status for Elvis and Hank (Brujo)

- Brujo's goal is for Elvis (linter, around a decade old) and Hank (dead-code detector, 2–3 years old) to be listed on erlang.org as the recommended tools. That status would be similar to rebar3 being the official build tool.
- Many developers still haven't heard of them.
- The OTP team has previously declined because running the tools on OTP's own codebase produces huge numbers of warnings. The group felt that isn't a good reason to exclude them for new code.
- Context: the rebar 4 goal is to ship rebar inside the Erlang distribution.
- Suggested next step: talk with the OTP team, and possibly have the EEF maintain or endorse an "official recommended tools" organization surfaced on the Erlang website.
